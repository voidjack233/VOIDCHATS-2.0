# Approved temporary encrypted relay

Approved on 2026-11-02 (Asia/Manila), including the owner's final adjustments: Go sets all event timestamps and a fixed 30-day deadline; advanced retry/deduplication and encrypted delivery receipts are deferred. The owner subsequently instructed "do the migration now". The exact SQL was verified in isolated PostgreSQL and applied on 2026-11-02 at 14:56 (Asia/Manila), followed by the matching backend. The live database has only accounts/messages; both accounts and registered keys were preserved. Credentials and Cloudflared remain unchanged.

The responsibility is Authenticate → Locate → Temporarily store → Relay → Acknowledge → Delete. VOID-ID is a permanent public routing/contact identifier. Registered Ed25519 key ownership authenticates an account; the identifier itself does not. Usernames are optional display metadata, never required for messaging.

The deployed database has only public.accounts and public.messages. Existing account UUIDs, VOID-IDs, authentication keys, timestamps and supplied usernames are retained. The applied migration makes the existing username column nullable; it does not remove that column or invent replacement names.

The queue stores exactly event_id, sender_void_id, recipient_void_id, payload, created_at and expires_at. The key is (sender_void_id,event_id). Go stamps UTC creation time once and derives expiry with 30 * 24 hours. Clients cannot submit either timestamp. Server acceptance occurs only after persistence commits. Authenticated recipient ACK deletes the entire row and ciphertext; expiry cleanup deletes remaining expired rows. No delivered column, history, tombstone or delivery-receipt state is retained.

Account initialization stays HTTP. Every ordinary message, lookup and ACK uses an authenticated WebSocket. The server keeps one active connection per account, uses bounded transport queues and quota/rate controls, and offers remaining unexpired events after reconnect. One event is in flight per recipient connection, opening the window on ACK/expiry. A lost ACK can stall delivery until reconnect or expiry. No automatic resend/backoff or exactly-once guarantee is implemented. Duplicate IDs still queued are rejected; reuse after deletion cannot be detected.

OpenMLS encryption and group state remain on devices. Public KeyPackages and Welcome objects can travel through an online-only opaque relay command while both authenticated peers are connected. The backend does not parse or store them, generate private keys, track conversations, or declare MLS readiness. Established conversation ciphertext can be queued while a recipient is offline without any fresh KeyPackage.

The earlier application incorrectly required a claimed KeyPackage and Welcome to create a contact request, made acceptance establish a server conversation, persisted two copies of message data in history/event tables, retained ACKed events for idempotency, and globally serialized messaging transactions. The approved design removes these workflows rather than making their dependencies optional. The superseded draft migration 004_decouple_message_requests.sql must not be applied; it has been replaced in this source.

Preserved/reused components are account registration, public-key validation, Snowflake account identifiers, account key lookup, fresh connection-bound authentication, connection replacement handling, writer/heartbeat/deadline machinery, admission and rate limits. The new queue adapter uses only scoped producer quota coordination, ordinary inserts and recipient-qualified deletes, with no global transaction lock or permanent cursors.

Retired components are server-managed requests, conversations, blocks, KeyPackage inventories/claims, persistent messaging sessions, HTTP message/sync/ACK endpoints, retained receipt events, and conversation sequencing. Client-side blocking cannot prevent queue consumption, and fresh-key bot registration remains a separate unresolved abuse issue. The scope is one logical active device per account.

The exact applied schema transition is [004_temporary_relay_queue.sql](../migrations/004_temporary_relay_queue.sql). It aborts if any legacy messaging/session/block/package table contains user data, including already ACKed records or expired sessions. The internal version 1 marker is the only removable row. Accounts are preserved. No automatic data conversion or deletion is attempted. Nonempty tables require a separately reviewed drain/export/import plan, because legacy message/client/event IDs and receipt formats do not map transparently to this minimal queue.

[Deployment review](MESSAGING_DEPLOYMENT.md) describes the guards, exact SQL effects and privilege file. [The API contract](MESSAGING_API.md) documents frames, proof bytes, resource limits and intentionally unresolved reliability behavior. Verification passed with mocks, in-memory stores, synthetic loopback servers and actual restricted-role PostgreSQL/WebSocket flows in a private cluster. The full live backup was restored and migrated there first; populated legacy data caused a verified atomic rollback. Live checks used readiness, retired-route responses and unknown-account WebSocket rejection only, with no account/message insertion. See [verification and activation](RELAY_VALIDATION.md).
